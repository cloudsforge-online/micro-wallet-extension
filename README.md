# micro-wallet-extension

[![ci](https://github.com/cloudsforge-online/micro-wallet-extension/actions/workflows/ci.yml/badge.svg)](https://github.com/cloudsforge-online/micro-wallet-extension/actions/workflows/ci.yml) [![TypeScript](https://img.shields.io/badge/TypeScript-strict%20ESM-3178C6?logo=typescript&logoColor=white)](./tsconfig.json) [![node](https://img.shields.io/badge/node-%3E%3D22-5FA04E?logo=nodedotjs&logoColor=white)](./package.json) [![manifest](https://img.shields.io/badge/manifest-v3-4285F4?logo=googlechrome&logoColor=white)](./manifest.chrome.json) [![EIP-6963](https://img.shields.io/badge/EIP--6963-multi--wallet-e8622c)](https://eips.ethereum.org/EIPS/eip-6963) [![licence](https://img.shields.io/badge/licence-MIT-blue)](./LICENSE)

CloudsForge's **self-custody** wallet for the browser. Chrome, Firefox, Opera and Edge — one
source, two manifests, four listings.

Design authority: [`ecosystem/25-wallet-clients.md`](https://github.com/cloudsforge-online/micro-docs/blob/main/ecosystem/25-wallet-clients.md)

```
pnpm install && pnpm check
```

`pnpm check` runs the type-check, both builds and the unit suite. The browser suite is separate
because it needs a running Hearth node:

```
pnpm build && pnpm test:e2e
```

---

## This is not `micro-wallet`

`micro-wallet` is **custodial** and good at what it does: it holds balances, `micro-custody` holds
the keys, and the ledger is the truth about what you own.

**This is the other thing.** Here you hold the key, and CloudsForge cannot move your money, sign for
you, freeze you, or lose you. There is no recovery, because there is nothing on our side to recover
from.

The single most dangerous thing this design can do is let somebody confuse the two, so §1.1 of the
design authority forbids ever summing a custodial and a self-custody balance into one number. That
rule is enforced here in three places: this extension cannot see a custodial balance at all, every
figure it draws carries a `self-custody — you hold the key` label generated by the stylesheet rather
than by markup, and the balance is drawn in a colour reserved for it.

## What ships

| Browser | Build | Manifest |
| --- | --- | --- |
| Chrome | `dist/chrome` | `manifest.chrome.json` |
| Opera, Edge | `dist/chrome`, unchanged | — separate listings, not separate products |
| Firefox | `dist/firefox` | `manifest.firefox.json`, gecko id, `strict_min_version: 128` |

The JavaScript is byte-identical between the two builds and a test asserts it, so a browser check
cannot creep in and quietly turn one listing into a different product.

| | |
| --- | --- |
| **Accounts** | Create from a new phrase, restore from an existing one, derive more from the same seed, import a raw key or a keystore, watch-only |
| **Money** | Balance, history read straight from blocks, send with an overridable fee, receive with a QR and a checksummed address |
| **Dapps** | EIP-1193 provider, EIP-6963 discovery, EIP-3085/3326 add and switch chain, `personal_sign`, `eth_signTypedData_v4` |
| **Confirmations** | The call is decoded, not shown as hex. Unlimited-approval warnings. The origin is named in full |
| **Safety** | Verified seed backup, a reveal that takes three deliberate steps, auto-lock on a `chrome.alarms` alarm, and a promise that the wallet never asks for the phrase again |

## The signing core is not in this repository

Every mnemonic, key, hash, signature and encoding comes from
[`@cloudsforge/hearth-wallet-core`](https://github.com/cloudsforge-online/micro-hearth-wallet-core),
consumed from the sibling checkout the way `micro-hub-web` consumes the design system. **There is no
cryptography in `src/`** — not a keccak, not a curve, not a keystore format.

That is the design authority's §3 and it is a hard rule rather than tidiness: three client shells
depending on divergent copies of a signer is the worst failure this architecture can have, and the
way it starts is one client reimplementing a small piece locally because the core was awkward. If
something is missing from the core, it is fixed in the core.

## The MV3 problem, which is the whole design

A manifest v3 service worker is **terminated after about thirty seconds of inactivity**. A user
reading a confirmation screen carefully — checking the address character by character, because this
wallet tells them to — takes longer than that. So the worker that received a request is routinely
not the worker that carries it out.

Everything in `src/background` is built around that:

- **No state that matters lives in a module variable.** There is no `let unlockedWallet`, no cache,
  no in-memory request map. The worker is a pure function of `chrome.storage` plus the message that
  woke it.
- The unlock lives in `chrome.storage.session`, which survives a worker restart, is never written to
  disk, and is unreadable from a content script.
- A request record is written to storage **before** the approval window opens, and the decision is
  written back to it. The request id is minted by the **content script**, which is the only
  participant guaranteed to live as long as the page that is waiting.
- Auto-lock is a `chrome.alarms` alarm, not a `setTimeout` — a timer dies with the worker, so a lock
  built on one fails *open*. The deadline is also re-checked on every privileged read, so the wallet
  cannot be used past it even with alarms entirely broken.
- The content script arms its own ten-minute deadline. **No promise this provider returns can hang
  forever**, whatever happens to the worker.

`test/e2e/worker-restart.test.ts` proves it by killing the service worker mid-approval, with CDP,
and then clicking Approve. It first proves the kill is real by showing the worker's global scope
comes back empty.

## Coexistence, and losing on purpose

Before EIP-6963 there was one global and every wallet wrote to it. The winner was whichever
extension the browser injected last, which is not a decision the user made.

This wallet **announces** over EIP-6963 and takes `window.ethereum` only if it is absent — and even
then leaves the property `writable` and `configurable`, so a wallet installed later can still have
it. If another wallet is already there, nothing happens: no wrapping, no proxying, no `providers`
array. §4.3 puts it best — *a wallet that wins that fight by force is a wallet users uninstall.*

`test/e2e/coexistence.test.ts` loads a **second unpacked extension** that behaves the way MetaMask
does, and asserts that both wallets are discoverable, that the rival keeps the global, and that this
wallet still reads the live chain through the 6963 path.

## Tests

**No `page.route` anywhere.** This estate once shipped 314 specified browser scenarios and a green
CI suite while sign-in was broken for every user, because every harness intercepted its own requests
and answered them from fixtures. The suite tested the fixtures.

So the browser suite drives a real Chromium with the real unpacked extension against a **real Hearth
node**, and if the node is not running it fails rather than skipping.

| Suite | What it is |
| --- | --- |
| `pnpm test` | Units: the QR encoder round-tripped through an independent decoder, call decoding, money arithmetic, and guards on the built package |
| `test/e2e/wallet.test.ts` | Onboarding, a balance read off the chain and checked against a direct RPC call, and a signature the **node's own decoder** recovers to the right address |
| `test/e2e/coexistence.test.ts` | EIP-6963 with a rival wallet installed |
| `test/e2e/worker-restart.test.ts` | The service worker killed mid-approval |

Two of these use an **oracle rather than a self-check**, which is the pattern the signing core
established: the QR encoder is checked by `jsQR` decoding its output, and the signature is checked by
`hearth/node/src/chain/transaction.js` — the running network's own implementation, not ours to adjust
when it disagrees. A self-check is a check that cannot fail.

The oracles earned their place. `jsQR` found three real defects in the QR encoder that every
self-consistent assertion had passed: a transposed format-information block, a zig-zag walk whose
last strip indexed `column -1` and silently wrapped onto the previous row, and a Reed–Solomon
generator polynomial built with its coefficients reversed. All three produced codes that looked
perfect and could not be scanned.

## Assets

**The icons in `dist/*/icons` are placeholders**, drawn by `tools/png.js` at build time. The build
prints a line saying so on every run.

`micro-wallet-assets` is being generated in parallel; §6 of the design authority specifies the
extension set as 16, 32, 48 and 128 plus toolbar icons in both polarities and a badge overlay for a
pending request. The build reads `../wallet-assets/assets/extension/` and uses the real files the
moment they exist, with no change here.

## What this repository deliberately does not do

- **No `eth_sign`.** It signs 32 arbitrary bytes with no prefix and no structure, so nothing can be
  shown to the user about what they are agreeing to. It is refused by name, with a message saying
  what to use instead.
- **No ABI lookup service.** A selector this wallet does not recognise is reported as unrecognised.
  Fetching an ABI would tell a third party which contract a user is about to touch.
- **No indexer.** History is read by walking blocks, so the wallet works against any Hearth node with
  every CloudsForge service switched off. The screen says how far back it looked rather than implying
  it has everything.
- **No telemetry.** §7: if it cannot be built without seeing an address, a balance or a transaction,
  it is not built.
- **No `<all_urls>` host permission.** A custom RPC endpoint is an *optional* permission, requested
  when a user adds one.
